01 / Executive brief

The product problem

Attendance is not a check-in button. It is a policy and exception system.

A student experiences attendance as a quick moment; a faculty member experiences it as a record that must be opened, reviewed, corrected, and defended. Campus technology and policy sit behind both. The interface must make that system understandable without pretending the power, privacy, and accuracy risks are simple.

The core product decision was to separate the temporary verification input from the official attendance record, keep faculty judgment in the correction loop, and give students visibility into status, history, and review paths.

01

Front-stage confidence

A focused mobile flow for checking in, confirming the result, reviewing history, and requesting review when the record is wrong.

02

Faculty operations

A responsive web workspace for opening sessions, resolving exceptions, correcting records, and identifying where a human follow-up may help.

03

Institutional governance

A proposed boundary around verification, retention, access, fallback, and audit—requiring campus policy and technical review.

i

Project scope: ImHere is a capstone product concept, not a deployed campus service. The screens and logic show the proposed experience. Privacy, accessibility, location accuracy, integrations, and usability would require validation with students, faculty, campus IT, and institutional stakeholders before implementation.

02 / Roles & decision rights

Service tensions

One shared record. Unequal power and very different jobs.

The design could not simply shrink a faculty dashboard into a student app. Each role has a different goal, urgency, and authority—and a student carries more risk when an automated check is wrong.

Student

“Did my check-in work?”

Students need a quick action and an unambiguous answer. They also need understandable data boundaries and a credible path to challenge an incorrect result.

  • See the active class and check in without searching.
  • Understand when location access begins and ends.
  • Confirm attendance immediately.
  • Review attendance and explain an absence.
Faculty

“Who needs my attention?”

Faculty need attendance to be faster than a manual process while retaining responsibility for late arrivals, technical errors, exceptions, and the final course record.

  • Open or close a session with minimal setup.
  • Scan the roster and spot exceptions quickly.
  • Correct a record without leaving the workflow.
  • Review patterns before deciding whether to reach out.
1

Low friction vs. informed choice

Check-in should be fast, but not so compressed that a sensitive location request becomes invisible or coercive.

2

Automation vs. due process

Verification can reduce work, but an error must remain reviewable by both the student and an accountable human.

3

Signals vs. labels

Patterns can help prioritize outreach, but the system should describe records and uncertainty—not define a student.

03 / State & data model

Proposed interaction architecture

Trust depends on visible state and explicit authority.

The concept uses a faculty-initiated session rather than passive, always-on tracking. The interface exposes when the window opens, what the verification is doing, when a record is final, and who can correct it.

01

Faculty opens attendance

The professor starts a short session for the selected course. Students enrolled in that course see the check-in become available.

02

Student reviews the request

Before requesting device permission, the interface explains that location is being used to verify proximity for this class session.

03

Presence is verified

The system checks whether the device is within the active classroom area. The intended record is an attendance result—not a location history.

04

Both sides receive status

The student sees a clear confirmation, while the faculty roster updates. Errors remain editable through a manual review path.

Two synchronized lifecycles

The faculty session controls availability; the student record can resolve immediately or move into accountable review.

Faculty session

  1. Scheduled
  2. Open
  3. Locked
  4. Audited or corrected

Student record

  1. Eligible
  2. Verifying
  3. Confirmed or needs review
  4. Resolved

Proposed data contract

Privacy is not solved by hiding technical complexity.

A trustworthy implementation would need plain-language consent, data-minimization rules, retention limits, a non-location fallback, and institutional review. The interface can communicate those decisions, but it cannot substitute for them.

Purpose limitation

Request a session-specific proximity result only while attendance is open—not ongoing location access.

Minimum record

Store the attendance status and an auditable correction history; define every retained field with campus stakeholders.

Excluded by default

Do not retain continuous coordinates, route history, background tracking, or location unrelated to the active session.

Fallback and appeal

Provide a non-location path and human review so device access or technical failure does not become an automatic penalty.

04 / Decision records

Interaction strategy

Every simplification carries a tradeoff.

The interface reduces effort where speed matters, but it does not hide consequential decisions. These records make the constraint, risk, and response reviewable by design, policy, and engineering partners.

Student dashboard

Make the next action unmistakable.

The active class and check-in state receive the strongest visual emphasis. Secondary information, such as history and absence requests, remains available without competing with the immediate task.

Tradeoff & response

A narrow task can bury secondary needs, so one dominant action is paired with persistent access to history, requests, and an explicit confirmation state.

Permission moment

Explain location before asking for it.

A short pre-permission screen gives context before the operating system prompt appears. It states the purpose, intended duration, and alternate path if verification fails.

Tradeoff & response

An extra step slows check-in slightly, but it supports informed choice through just-in-time explanation, visible session status, and a route to review.

Faculty roster

Surface exceptions without defining the student.

The dashboard prioritizes attendance events that require review. Labels describe the record—such as absent, late, or unresolved—rather than assigning an automated identity to the student.

Tradeoff & response

Prioritization can create stigma, so the system labels the record, exposes uncertainty, supports inline correction, and keeps outreach a human decision.

Error recovery

Assume the ideal flow will fail sometimes.

GPS accuracy, connectivity, permissions, and device access can all create false negatives. The concept therefore includes correction and absence-documentation paths.

Tradeoff & response

Fallback creates operational work and potential misuse, but that cost is preferable to automatic penalties from technical failure.

06 / Interface system & design QA

Delivery quality

One product language, two densities, explicit states.

Hope-inspired navy and orange create continuity, while shared components and status language connect the student and faculty experiences. Density changes by task; the meaning of actions, records, and states does not.

  • Primary navy#002855
  • Accessible action orange#B84A10
  • Warm paper#FBFAF7
  • Core text#17202A
  • Shared state grammar

    Available, verifying, confirmed, late, unresolved, awaiting review, and corrected states use consistent language across roles.

  • Responsive density

    Mobile prioritizes one action; faculty layouts expand into queues, tables, and trends without changing the underlying record model.

  • Color plus language

    Status is communicated through text, hierarchy, and structure rather than green, yellow, or red alone.

  • Input and navigation

    Primary actions and roster controls need visible focus, keyboard operation, generous targets, and clear saved or error feedback.

  • Consequential copy

    Permission, error, review, denial, and correction language must explain purpose, state, ownership, and next action.

  • Formal QA still required

    Contrast, screen-reader output, responsive behavior, motion, data tables, permissions, and real-device use require documented testing.

07 / Governance & validation

Responsible rollout

A credible launch needs policy, technical, and experience validation in parallel.

Design cannot approve this service alone. Location verification, student records, accessibility, identity, integrations, appeals, and faculty workflow require named decision owners and evidence before a campus pilot.

Product & design

Own the experience contract

Define states, language, fallback, review paths, responsive behavior, instrumentation, and the evidence required to change direction.

Campus IT & security

Own technical trust

Review authentication, enrollment and records integrations, data minimization, reliability, device support, logging, and incident response.

Privacy, access & records

Own institutional safeguards

Define consent, retention, access, accessibility, equity, appeals, legal obligations, and what the service must never infer.

Students & faculty

Validate lived use

Evaluate comprehension, classroom fit, technical failure, pressure, workload, correction, and whether the fallback is genuinely equivalent.

Measures tied to the riskiest assumptions

Student success

Fast, clear, recoverable

Evaluate whether the flow reduces effort without sacrificing understanding or control.

  • Check-in completion and time on task
  • Result and permission comprehension
  • Recovery success without faculty help
Faculty operations

Efficient, accountable review

Measure whether the workspace saves effort while preserving correction and judgment.

  • Session setup and close time
  • Time to identify and correct an exception
  • Request-queue age and resolution rate
Accuracy & equity

No penalty from technical failure

Compare outcomes across verification and fallback paths, devices, access needs, and conditions.

  • False-negative and false-positive rates
  • Fallback completion and parity
  • Statuses overturned after human review
Trust & reliability

Understandable and supportable

Track the signals that reveal unclear policy, fragile technology, or hidden operational cost.

  • Permission understanding and refusal reasons
  • Verification errors and support contacts
  • Audit, access, and data-handling exceptions

A staged path from concept to pilot

Phase 01 · Align

Define policy and ownership

Co-design the service boundary with students and faculty while campus partners resolve decision rights, retention, fallback, and integration constraints.

Phase 02 · Stress test

Test the risky states

Run prototype and device tests across permissions, GPS variance, low connectivity, keyboard and screen-reader use, correction, and appeal.

Phase 03 · Limited pilot

Learn before scaling

Pilot with a constrained course group, monitor privacy-conscious measures, review harm and support signals, and require a go/no-go decision before expansion.

This is a proposed governance, measurement, and validation framework—not evidence of launch performance. No accuracy, efficiency, compliance, adoption, or student-outcome claim is made here.
08 / Reflection

Strategic takeaway

The product is only credible when policy, interface, and system state agree.

The strongest outcome of the design work is a more coherent operating model: explicit roles, synchronized states, minimum-data boundaries, human correction, responsive interfaces, and a measurable path to validation. My technical background helps connect those decisions to implementation; UX keeps the model accountable to the people affected by it.

01

One record, two roles, one governance layer

The student and faculty experiences differ in density and authority while remaining connected by the same status model and accountability rules.

02

Fallback is part of the core service

Privacy, false negatives, device access, and appeals cannot be treated as edge cases when an attendance error can affect a student.

03

States and criteria bridge design to build

The lifecycle, decision rights, data contract, responsive UI rules, and validation measures create concrete questions for cross-functional delivery.
