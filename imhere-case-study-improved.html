ImHere Attendance

A role-based attendance concept designed to make classroom check-in fast for students, manageable for faculty, and transparent about when location data is being used.

My focus UX strategy, interaction design, UI design
Context Cross-functional university capstone
Users College students and faculty
Deliverables Mobile flows, faculty dashboard, system concept
Overview Challenge System flow Design decisions Screens Trust & accessibility Reflection
01 / Overview

The opportunity

Move attendance out of the way of teaching.

Attendance is a small classroom task with an unexpectedly complex service behind it. Faculty need a dependable record and a quick way to correct exceptions. Students need to know whether they checked in successfully, how absences affect them, and why the system is requesting location access.

ImHere explores one connected experience: a lightweight student check-in paired with a more detailed faculty workspace. My design focus was translating technical constraints into understandable moments—especially around location permissions, session status, and error recovery.

01

Student experience

A focused mobile flow for checking in, confirming attendance, reviewing history, and submitting an absence explanation.

02

Faculty experience

A dashboard for opening sessions, reviewing attendance, correcting records, and identifying patterns that may warrant a human follow-up.

03

System model

A proposed time-limited location check designed to verify presence without presenting the product as continuous tracking.

i

Project scope: ImHere is a capstone product concept, not a deployed campus service. The screens and logic show the proposed experience. Privacy, accessibility, location accuracy, integrations, and usability would require validation with students, faculty, campus IT, and institutional stakeholders before implementation.

02 / Challenge

Two perspectives

One attendance record. Two very different jobs.

The design could not simply shrink a faculty dashboard into a student app. Each group enters the experience with a different goal, level of urgency, and concern.

Student

“Did my check-in work?”

Students need a quick action and an unambiguous answer. They also need control over sensitive information and a clear path when something goes wrong.

  • See the active class and check in without searching.
  • Understand when location access begins and ends.
  • Confirm attendance immediately.
  • Review attendance and explain an absence.
Faculty

“Who needs my attention?”

Faculty need attendance to be faster than a manual process, while retaining the ability to resolve late arrivals, technical errors, and exceptions.

  • Open or close a session with minimal setup.
  • Scan the roster and spot exceptions quickly.
  • Correct a record without leaving the workflow.
  • Review patterns before deciding whether to reach out.
1

Keep the student task narrow

The active check-in should be the most obvious element on the screen, supported by class context and a clear success state.

2

Explain sensitive requests

Permission language should describe what is requested, why it is needed, and what the user can do when access is unavailable.

3

Design for exceptions

The experience needs recovery paths for inaccurate location, device issues, late arrivals, and faculty corrections—not only the ideal flow.

03 / System flow

Proposed interaction model

A short attendance window with visible boundaries.

The concept uses a professor-initiated session rather than passive, always-on tracking. That boundary is reflected in the interface so the user is not expected to infer what the system is doing.

01

Faculty opens attendance

The professor starts a short session for the selected course. Students enrolled in that course see the check-in become available.

02

Student reviews the request

Before requesting device permission, the interface explains that location is being used to verify proximity for this class session.

03

Presence is verified

The system checks whether the device is within the active classroom area. The intended record is an attendance result—not a location history.

04

Both sides receive status

The student sees a clear confirmation, while the faculty roster updates. Errors remain editable through a manual review path.

Design boundary

Privacy is not solved by hiding technical complexity.

A trustworthy implementation would need plain-language consent, data-minimization rules, retention limits, a non-location fallback, and institutional review. The interface can communicate those decisions, but it cannot substitute for them.

04 / Decisions

Interaction design

Design choices tied to observable user needs.

Rather than using psychological terminology to justify every detail, I focused the interface around task priority, system feedback, error prevention, and legibility.

Student dashboard

Make the next action unmistakable.

The active class and check-in state receive the strongest visual emphasis. Secondary information, such as history and absence requests, remains available without competing with the immediate task.

Design response

One dominant action, contextual class information, and a confirmation state that does not rely on color alone.

Permission moment

Explain location before asking for it.

A short pre-permission screen gives context before the operating system prompt appears. It states the purpose, intended duration, and alternate path if verification fails.

Design response

Just-in-time explanation, visible session status, and a route to instructor review.

Faculty roster

Surface exceptions without defining the student.

The dashboard prioritizes attendance events that require review. Labels describe the record—such as absent, late, or unresolved—rather than assigning an automated identity to the student.

Design response

Scannable status chips, filters, inline correction, and human judgment before outreach.

Error recovery

Assume the ideal flow will fail sometimes.

GPS accuracy, connectivity, permissions, and device access can all create false negatives. The concept therefore includes correction and absence-documentation paths.

Design response

Actionable error messages, manual faculty override, and a visible pending-review state.

Student screens use generous spacing and a narrow task focus. Faculty screens support denser information while preserving hierarchy, readable status labels, and direct correction paths. Select any screen to enlarge it.

06 / Trust & accessibility

Visual system

Calm enough for students. Structured enough for faculty.

The interface uses Hope-inspired navy and orange as anchors, supported by warm neutral surfaces. Color communicates emphasis, but text labels and hierarchy carry the meaning.

Primary navy#002855
Action orange#D45A18
Warm paper#FBFAF7
Core text#17202A
Visible system status

Students can see whether check-in is available, successful, unavailable, or awaiting review.

Color plus language

Status is communicated through text and structure, not green, yellow, or red alone.

Readable interaction targets

Primary actions and roster controls are designed with generous touch and click areas.

Permission clarity

Location access is introduced with purpose, timing, and a recovery path before the device prompt.

Reduced interruption

The student flow minimizes steps during class and reserves detail for the dashboard.

Validation still required

Contrast, keyboard behavior, screen-reader output, motion, and real-device use should be formally tested.

07 / Reflection

What the project demonstrates

Designing the interface meant designing the boundaries.

ImHere pushed me to think beyond individual screens. The most important decisions were about roles, permissions, system state, data sensitivity, and exception handling. My computer science background helped me ask how the interaction could map to a buildable system; the UX work kept the technical model accountable to the people using it.

01

What worked

A clear separation between the lightweight student task and the information-dense faculty workflow.

02

Biggest risk

Location verification can create privacy concerns and false negatives. Trust requires policy, technical safeguards, and fallback—not only reassuring copy.

03

What I would test next

Permission comprehension, check-in completion, GPS edge cases, no-location alternatives, faculty correction speed, and accessibility with assistive technology.
