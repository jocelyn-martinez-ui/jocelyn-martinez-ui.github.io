01 / THE QUESTIONDESIGN BRIEF

What makes
a design ready?

A file can look finished while the decision behind it is still unresolved.

This concept explores the gap between creative critique and production release. The central challenge: give a designer, reviewer and producer a common understanding of which version is current, which changes remain open, and what is actually approved.

PROOF is a self-directed, AI-assisted design exploration—not commissioned software. The workflow and example briefs are fictional; no interviews, client releases, usability results, production claims or efficiency gains are implied.

PRIMARY USERSIn-house designers, creative reviewers, print producers
CONSTRAINTNo hidden approval; revision history must stay legible
DESIGN ROLEInteraction, brand, interface, information design, code
DELIVERABLESWorking workflow, visual system, print-proof specimen
02 / USER EXPERIENCERESPONSIBILITY BEFORE AUTOMATION

Separate the file
from its decision.

A status is only useful if it explains what can happen next.

Three common needs informed the design hypothesis: a reviewer needs an exact version to assess; a designer needs actionable feedback tied to that version; a producer needs an explicit release before preparing outputs. These are reasoned scenarios, not observed participant findings.

01 / ASSIGN

Identify the proof

Each job names its deliverable, size and revision. Feedback is tied to that revision—not an unnamed attachment.

02 / REVIEW

Decide, with context

Request a change with a reason, or approve the current revision explicitly. A blank note cannot masquerade as feedback.

03 / RELEASE

Protect the handoff

A production sheet is blocked until review and preflight are complete. A revised proof clears its earlier approval.

Interaction principleState + version + owner + next action belong together. Approval must be reversible through an explicit new revision, not silently overwritten.
03 / ART DIRECTIONA WORKING GRAPHIC LANGUAGE

Make precision
feel alive.

PROOF borrows the rhythm of prepress marks, numbered editions and editorial marginalia.

Cobalt carries the identity; pale stock allows dense information to breathe; citron singles out actions that change the state of a proof; vermilion is reserved for unresolved blockers. Typography combines a confident, compressed sans voice with functional mono-style specifications and a contrasting italic editorial tone.

    STATE MODEL

    Awaiting review → Changes requested → New revision → Approved → Preflight complete. A new revision invalidates any previous release gate.

    INTERACTION DETAILS

    Required feedback, contextual disabled state, focus restoration, live announcements, readable revision log and print-specific output are part of the model.

    BOUNDARY

    Everything is simulated locally. It is not an approval service, document store, file converter, e-signature or professional print preflight tool.

    05 / EVALUATIONWHAT THIS PROVES — AND WHAT IT DOESN'T

    A system that
    owns its limits.

    The prototype demonstrates interaction architecture and a tangible graphic system—not validated workflow effectiveness.

    Design choices can be inspected: release depends on the currently reviewed revision, every decision is named in a history list, and print preflight remains distinct from approval. This reduces ambiguous states within the prototype. It does not establish that real users would understand or adopt the system.

    Next validation: conduct moderated walkthroughs with designers, reviewers and producers; assess task completion, error recovery, terminology comprehension and version attribution; prototype real file uploads and vendor constraints; audit keyboard and screen-reader use in production browsers.

    01 / STRENGTH

    Meaning before motion.

    Explicit labels and stable state changes carry more weight than decorative transitions.

    02 / TRADEOFF

    Less automation, more trust.

    Separating approval from preflight adds steps, but avoids treating an aesthetic sign-off as production clearance.

    03 / FUTURE

    Validate in context.

    Real vendor constraints, auditability and multi-user permissions remain important untested requirements.
